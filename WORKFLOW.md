## 1. 🧬 DEVELOPMENT LIFECYCLE

### A. Branching Strategy

Direct commits to `master` are **FORBIDDEN** (except for release commits
generated by scripts).

**Format:** `type/kebab-case-description`

**Types:**

- `feat/` — New features (e.g., `feat/streaming-parser`)
- `fix/` — Bug fixes (e.g., `fix/worker-race-condition`)
- `refactor/` — Code changes without behavior change
- `chore/` — Config, scripts, deps (e.g., `chore/update-webpack`)
- `docs/` — Documentation only

Command:

- `git switch -c feat/streaming-parser-v1`

---

### B. The Coding Standard (Law)

1. File Identity Headers (MANDATORY)  
   Every source file (`.ts`, `.rs`, `.js`, `.ps1`) MUST start with a relative path
   comment.

Auto-fix:

- `pwsh ./scripts/add-headers.ps1`

2. No `console.log`  
   Use:

- `logger.info()`
- `logger.warn()`
- `logger.error()`

Exception: temporary local debugging, but must be removed before push.

3. Strict Typing

- `any` is banned. Use `unknown` + type guards.
- Interfaces must be explicit.

4. Error Handling

- Never swallow errors.
- Always use `normalizeUnknownError(e)` before logging.
- UI must gracefully degrade (toast/banner), never white-screen.

## 2. 🛡️ THE GUARDIAN GATE (VERIFICATION)

The Guardian (`scripts/verify-all.js`) is the supreme authority. If it fails,
your code does not exist.

LEVEL 1: Quick Verify (During Dev)  
Runs linting, formatting check, and fast compilation. Skips heavy tests:

- `npm run verify:all -- --fast --no-push`

LEVEL 2: Full Verify (Pre-Commit)  
Runs everything except the heaviest audit checks. Includes Unit Tests with coverage:

- `npm run verify:all -- --no-push`

LEVEL 3: Strict Verify (Pre-Push / Release)  
The complete battery of tests. This is what CI runs:

- `npm run verify:all:strict -- --no-push`

Checklist executed by Guardian:

- Header Check: Are file paths present and correct?
- Conflict Check: Are there any `<<<<<<<` git markers?
- Big File Gate: Are there committed files > 5MB?
- Security Sniffer: Scans for secrets/keys in code.
- I18n Integrity: Are all keys in `sr.ts` present?
- Rust Gates: `cargo fmt` (check), `cargo clippy` (no warnings), `cargo test`.
- Build Gate: Does `npm run build` (Webpack prod) succeed?
- Test Gate: `vitest run --coverage` (Threshold: 80% global).
- E2E Gate: `playwright test` (Headless browser smoke tests).

## 4. 🚀 COMMIT, PUSH & PR

Commit Protocol: Conventional Commits (required for automated changelog generation)

- `feat: ...` -> Minor version bump (1.1.0)
- `fix: ...` -> Patch version bump (1.0.1)
- `BREAKING CHANGE: ...` -> Major version bump (2.0.0)

Push Sequence:

1. Final check:
    - `npm run verify:all -- --no-push`

2. Stage & commit:
    - `git add .`
    - `git commit -m "feat: implement streaming xml parser with quick-xml"`

3. Push:
    - `git push -u origin feat/streaming-parser`

Husky Hooks:

- `pre-commit`: runs linter and conflict checks
- `pre-push`: runs TypeScript type-check and basic tests
- bypass: `--no-verify` only in extreme emergencies (saving WIP)

## 6. 🚑 TROUBLESHOOTING

A) WASM module not found / File not found (Webpack)  
You likely cleaned the project but didn't rebuild WASM:

- `npm run build:wasm`

B) Office.js is not defined (tests)  
Ensure you mock Office global in `tests/setup.ts`.

C) TextEncoder is not defined (Worker tests)  
Ensure `src/taskpane/worker/transliteration.worker.ts` has the polyfill import at
the top.

D) E2E tests failing randomly  
Increase timeout in `playwright.config.ts` (Word Online init can be slow).

E) CodeQL “flapping” (alerts appear/disappear / Fixed ↔ Reappeared)  
If Code Scanning results randomly fail/pass for the same PR (especially on
`refs/pull/*/merge`), it almost always means **multiple workflows are uploading
CodeQL SARIF** for the same PR (duplicate CodeQL runs).

Fast local check (source of truth):

- `rg "codeql-action/(init|analyze|upload-sarif)" .github/workflows`

Expected: only **one** workflow file should contain CodeQL uploads
(typically `.github/workflows/codeql.yml`).

If you see CodeQL steps in multiple workflows (for example in `release.yml`),
remove/disable them (or at minimum ensure they do not run on `pull_request` and
do not upload SARIF), otherwise PR status can “flip-flop”.
